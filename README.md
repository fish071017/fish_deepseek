# 像素街机 PIXEL ARCADE

三款像素风手机小游戏，单文件零依赖。竖屏、单手、短单局，难度不友好。

> **变更（v5）**：按玩家反馈**删除了「箭头开路」**；「像素跳跃」改为岩浆上升 + 横向自动吸附；
> 「像素试管」重写打乱逻辑并加了完整撤销/重做。

## 怎么玩

**手机上（推荐）**

```powershell
# 在 pixel-arcade 目录下起一个本地服务
node _check\server.js
# 然后手机浏览器打开 http://<你电脑的局域网IP>:8123/
```

或者把整个 `pixel-arcade` 文件夹丢到任意静态托管（GitHub Pages / Vercel / Netlify / 对象存储），
手机访问 URL 后会提示「添加到主屏幕」——装完就是全屏 App，断网也能玩。

**完整部署步骤见 [`DEPLOY.md`](DEPLOY.md)**（含 GitHub Pages / Cloudflare Pages / 拖拽上传三种方案）。
上线前先跑一次自检：

```powershell
node _check\preflight.js
```

**电脑上**：直接双击 `index.html` 即可（游戏能玩；离线缓存需 https 才生效）。

## 三款游戏

| 游戏 | 玩法 | 上头点 |
|---|---|---|
| **像素试管** | 把同色方块倒进同一个瓶子；完整撤销/重做，走进死局随时退回 | 开局必定打乱，但空管和混色度是要平衡的 |
| **一指点色** | 判定线下方一排颜色按钮；按颜色消除方块，按错弹提示音并断连击 | 速度随时间上涨，来不及看清颜色 |
| **像素跳跃** | 长按蓄力、松手起跳，横向自动吸附下一个平台；下方岩浆持续上升，碰到底部即死 | 只能一直往上，停不下来 |

## 设计取舍

难度按「折磨优先」调（参考《羊了个羊》路线），但**绝不做不可解的关卡**：

- **试管**：从「已通关」状态反向打乱，每一步都是合法操作，所以正着走一定能解回去。
- **箭头**：反向放置生成——每个箭头落位时它的路径必然是空的，
  因此按落位逆序点就一定能清空。规则上「点一个只消一个」，
  保证不会因为一次点击引发不可控的全盘雪崩（这个坑踩过，见下）。

## 踩过的坑（备查）

1. ~~**箭头玩法第一版是错的**~~ → **该游戏已按玩家反馈整体删除**。
   原始教训保留：原设计「点一个箭头，撞飞路径上所有箭头」，
   量化后发现**一次点击就能清空整个盘面**（最优点击数恒为 1）。
   改成依赖解谜后能玩，但玩家反馈"根本不存在箭头、体验差"，最终下架。

2. **固定逻辑分辨率会被裁**：最初写死 360×640 并按 cover 缩放，
   在 19.5:9 的手机上左右两侧被切掉，静音键和最高分都看不见。
   改成**宽度固定、高度按设备宽高比推算**，全宽永远完整可见。

3. **不要用 `window.innerWidth` 定画布尺寸**：某些环境下它与真实视口不一致
   （本机无头 Edge 就报 492 而实际视口 390），会导致画布溢出被裁。
   改用 `canvas.clientWidth` + CSS `100dvh`。

4. **顶栏文字会重叠**：游戏名居中 + 右侧状态读数在窄屏上必然撞车。
   改成左中右水平分区。

5. **试管关卡开局就是「已完成」**（玩家点不动，等于没法玩）。
   打乱循环里搬的是**整管方块**（`n=4`），而整管搬运永远不会打破颜色分组，
   290 次迭代只是在排列整管顺序，最终仍是已解状态。
   改成**每次只搬 1 块**，并加一条兜底强制打破分组。
   教训：我的测试当时覆盖 `m.layout` 的时机写反了，等于绕过了真实路径才漏掉它；
   现在测试会显式断言「开局 `isSolved()` 必须为 false」。

6. **场景切换后首帧崩溃**：`App.go("game")` 是在 `home.update` 里同步调用的，
   于是**同一帧内 `Scenes.game.draw()` 就被调用，而它自己的 `update()` 还没跑过**，
   `draw()` 里读 `this.backRect` 直接抛异常，主循环整个挂掉。
   3x 高分屏侥幸没触发（时序不同），360×640 必崩。
   修法：凡是 `draw()` 会读的状态，一律在 `enter()` 里初始化。

7. **点击会被无条件丢掉**：`Input.endFrame()` 原来在每次 rAF 回调里清空 `taps`，
   但 rAF 回调次数和"帧"不是一一对应。如果一个回调在触摸事件之后、
   下一次 `update` 之前跑过一次，这一帧的点击就永远消失了 ——
   表现为"偶尔能点动"，极难复现。改成显式输入队列：
   事件进 `pending`，`update` 前快照进 `taps`，`update` 后才清空。

8. **验证脚本自己会骗人**（这一条花了最久）：反算触摸坐标时我用了
   `window.devicePixelRatio`，而应用里 dpr 被 `Math.min(dpr, 2.5)` 钳制，
   3x 屏上两者不等（3 vs 2.5），导致模拟点击整体偏移，
   于是把"应用完全正常"误判成"四款游戏全都点不动"。
   还犯过一次量纲错误：拿"应用回算的逻辑坐标"去比"派发的 client 坐标"。
   现在 `mobile.js` 明确以**逻辑坐标**为唯一基准。

9. **倒水倒出黑色方块**（玩家报告）：动画结束时按"数量 n"重新 `pop()` 源管，
   但方块在动画开始时就已被弹出，第二次 `pop()` 拿到的是 `undefined`，
   渲染时 `PALETTE[undefined]` 为 `undefined`，`fillStyle` 设成它就成了黑色，
   而且颜色永远匹配不上 → 卡关。
   **修法：动画开始时把方块值本身取出来存进 `pouring.moving`，结束时原值放回。**
   教训：凡是"先扣数据、过一会儿再补回来"的写法，都要存**值**而不是**数量**。

10. **跳跃高度是拍脑袋给的**（玩家报告）：初速度原本是
    `-MAXJUMP*0.62*(0.35+charge*0.65)-120`，满蓄力只上升 **31px**，
    而平台间距 **74px** —— 永远跳不上去，必现死局。
    改成从目标高度反推：`v = sqrt(2*g*h)`，并让最大间距硬性小于满蓄力高度。
    现在有断言守着：`满蓄力高度 > 最大平台间距`。

11. **箭头入场动画会让人以为盘面是空的**：`spawn` 从 0 涨到 1 需要约 0.4s，
    期间箭头尺寸为 0。手机上加载慢时很容易看到空盘，误以为"没有箭头"。
    改成生成时 `spawn = 1`，立即显示。

12. **`canvas.width` 赋值会清空画布**：手机地址栏收起/弹出会频繁触发 `resize`，
    原来无条件写 `canvas.width/height`，画面会被反复清空，
    表现为"突然一片空白"。改成尺寸真正变化时才赋值。

13. **打乱循环里藏着一个"撤销陷阱"**（玩家报告"只有一根管能动"）：
    `canPour` 允许「把方块倒到同色堆顶上」——**这恰恰是撤销上一步**。
    这类操作在候选里占多数，随机选择就反复撤销，
    实测跑 250 步后混色管数量为 **0**，颜色分组完好无损。
    **修法：打乱时禁止同色堆叠**，只允许"倒到异色顶上"或"倒进空管"。
    这两种推进操作都是合法操作的逆向，可解性依然成立。
    → 混色管从 0 变成 11+，纯色"已完成"管从 4.6 根降到 0.5 根。

14. **"够混"和"留空管"是互相冲突的**：总槽位固定时，盘面越散就几乎占满所有管子，
    空管自然变少（实测只剩 0.2 根）。得从源头**多给管子**（`colors + 空管 + 2`），
    再在生成时按"空管达标是硬门槛"来挑选打乱结果，才能两者兼得。

15. **横向吸附不能每帧重算目标**：玩家上升越过目标平台后，
    "最近的上方平台"会突然切换，横向速度反向，容易把人甩飞。
    改成**起跳瞬间锁定目标**，整个滞空期间不变。

16. **粒子错位**：`Fx` 粒子系统用的是屏幕坐标（在 `ctx.restore()` 之后绘制），
    但跳跃游戏喂进去的是世界坐标，平台越往上偏得越离谱。
    修法是喂屏幕坐标（`pl.y - camY`）。

17. **写文件时别引入 BOM**：用 PowerShell 改文件会加上 UTF-8 BOM，
    导致 `manifest.webmanifest` 解析失败（JSON 不允许开头有 BOM）、
    `sw.js` 也可能注册失败。要用 `UTF8Encoding($false)` 写入。
    `preflight.js` 现在会检查这个。

18. **移动平台漂出屏幕再也不回来**（玩家报告）：
    碰撞边界时只写了 `pl.vx *= -1`，**没有把位置夹回范围内**。
    一旦越过边界，`pl.x` 会持续累加漂出去，而越界判断永远为真、
    每帧翻转一次速度 —— 平台就永久留在屏幕外。
    实测平台漂到 **x=1540**（屏幕宽 360）。
    **修法：翻转速度的同时必须夹回位置**，再补一道屏幕范围夹取。
    现在 x 范围稳定在 8~352。

19. **平台间距"看着够得着其实够不着"**（玩家报告）：
    原来的 `gapMax = MAX_GAP - horiz * 0.18` 有两个问题：
    ① `horiz` 是**中心到中心**的距离，而玩家可能站在平台边缘，
       实际要走的横向距离更大；
    ② 没考虑水平速度从 0 加速到上限需要时间。
    **修法：用真实抛物线反推可达高度**（`horizontalReach(rise)`），
    并按中心距 × 安全系数 0.88 收敛。现在断言检查 2600 对平台，最小余量 35px。

20. **断言必须做变异测试**：修完移动平台后我的断言一开始是 **假绿**
    （用有 bug 的代码跑也通过）。原因是断言里我**自己复刻了一遍移动逻辑**，
    而不是调用游戏真实的 `update()`。改成调用真实代码后，
    还原 bug 立刻报 `出屏 54434 帧`。
    教训：断言要跑被测代码本身；写完一定要"故意改坏"验证它真的会失败。

## 排查手法（下次直接复用）

`?debug=1` 打开首页会显示诊断读数，第一行就是**构建版本**——
如果手机上显示的不是最新版本号，就是 Service Worker 缓存了旧代码。

改完代码记得同时改两个地方：`index.html` 的 `BUILD` 和 `sw.js` 的 `VERSION`。

### 真机触摸验证

`node _check/mobile.js` 用 Chrome DevTools Protocol 驱动真实 Edge，
在 4 种视口下派发真实触摸事件。它做的是**状态断言**（倒水后盘面变没变、
消箭头数减没减、得分涨没涨），不是截图比对，所以能抓到逻辑 bug。

写这类脚本最容易踩的两个坑（我都踩过，见上面第 8 条）：
反算坐标必须用应用自己的 `layoutRect.dpr`，且基准量要统一。
